# 采集与核验规则（智能体运行 SOP）

> 本文件是每次运行的唯一判定依据。运行前必须完整读取本文件与 `来源清单.md`。

## 一、目标与产出

在公开网络上发现**武汉市**（含 13 个行政区及东湖高新区、武汉经开区、临空港经开区、长江新区等功能区）的民生诉求与涉企诉求线索，输出**条目式报告**，并维护累积台账。

产出两份：
1. `报告\YYYY-MM-DD_HHMM.md` —— 本期报告（条目式，给人看）；
2. `数据\线索台账.jsonl` —— 累积台账（给程序看，一行一条 JSON，只增不删；状态变化追加 `status_history`）。

被剔除的事项写入 `数据\剔除记录.jsonl`。

## 二、时间窗口

- 默认窗口：**最近 14 天**，其中 7 天内的优先核验；每日首期回溯 14 天补漏。
- 旧线索（>14 天）仅在**状态有更新**（新回复、转办、办结、二次投诉）时纳入，并在报告"状态更新"区列出。
- 每次运行先记录本次实际运行时间与窗口，写进报告页眉。

## 三、线索定义

### 民生诉求
市民个人或家庭在公共服务、城市管理、住房、教育、医疗、社保、交通、环境、消费维权等方面，向政府或公共服务单位提出的、**尚未妥善解决**的诉求。

典型：物业纠纷、延期交房/办证、噪声油烟扰民、停水停电停气、道路破损、学位与入学、医保报销、拖欠工资（个人）、预付卡退费、政务办事卡壳。

### 涉企诉求
市场主体（企业、个体工商户）在**开办、经营、监管、政策兑现**中遇到的困难或不公。

典型：拖欠账款/工程款、政策补贴不兑现、审批与许可拖延、执法争议、乱收费乱罚款、融资难、用工与社保、园区配套、招商承诺未落实、涉企服务窗口问题。

**不属于本智能体范围**：纯咨询、纯表扬、纯建议且无具体诉求对象的；已进入诉讼/仲裁且无行政诉求的（可在备注注明）；招聘广告、房产中介广告、营销软文；非武汉辖区事项。

### 渠道覆盖要求（每期必查）
至少覆盖：① 市政府门户"来信公示"；② 2 个委办局"来信公示/局长信箱"；③ 武汉城市留言板；④ 人民网领导留言板、12345 官方渠道内容，或 12345 未解决诉求的媒体公开报道；⑤ 1 个社会投诉平台（黑猫/微博等）；⑥ 涉企专项检索 2 条。

零产出渠道处理：
- 连续 3 期零产出：报告"来源覆盖与局限"写明原因，下期该渠道检索式减半（降权）；
- 连续 5 期零产出：暂停该渠道，直到发现新入口或人工确认恢复。

## 四、纳入与剔除判定

### 纳入（满足其一）
| 状态 | 判定依据（原文须有对应表述或客观缺失） |
|---|---|
| 未办结 | 页面无任何办理回复；或仅"已受理/已转办" |
| 处理中 | "正在办理""已转交""督办中""合并处置"等 |
| 已回复未办结 | 官方已回复，但含"已要求/已督促/持续/计划/正在申请/待经费到位后/下一步"等未完成表述，或诉求只解决了一部分 |
| 办结不满意 | 有回复但诉求人明确表示不认可/未解决/将再次投诉；或回复答非所问、以"已告知途径"代替解决且诉求未落实 |
| 超期未回复 | 超过平台承诺时限仍无回复（须有发布时间佐证） |

**关键口径**：政府官网/部门公示里的"已回复"只是办理进度标记，**不等于办结**；只有回复中出现完成性结论，才可判为已办结。

### 剔除（须同时满足）
1. **官方渠道或官媒已公开**：中央/省/市官方媒体（长江日报、武汉广播电视台、湖北日报、湖北广播电视台、新华社、人民日报、人民网、央视等）或其官方账号，或政府门户"来信公示"、委办局信访公示等官方渠道已公开；**且**
2. **已明确办结**：报道或官方回复中出现"已解决/已办结/已整改完成/已修复/已退款/诉求人满意/隐患已消除"等结论性表述。

不满足其一即**保留**：官媒报道了但仍在处理 → 保留并标注"官媒已报道"；已回复但诉求未落实 → 保留并标"处理中/办结不满意"。

补充口径：
- 官媒报道了，但报道本身写的是"正在施工/正在整改/将限期完成/尚未完工/仍在协调" → **保留**，标"官媒已报道（未完工）"；
- 报道称"已解决"，但同一诉求的其他事项仍未落实 → **保留**，摘要写明哪部分未落实。

### 工作文书黑名单（一律剔除，即使出现姓名/单位）

以下内容属于政府工作文书或政务公开信息，不是市民诉求，**不因含具体人名而保留**：
- 人大建议答复、政协提案答复、人大代表建议/政协委员提案办理情况、建议提案办理情况通报；
- 政策解读、通知公告、规划公示、征求意见稿、政府工作报告、部门预决算、权责清单、收费清单、政府采购/招标公告、人事任免、统计数据、新闻发布会、领导调研与会议报道、办事指南、平台入口与填报说明。

常见误判排除：
- 12345/市民热线官方账号发布的"已妥处"合集 = 官媒/官方渠道报道 + 已办结 → 剔除；
- "已回复/已受理/已转办/已要求整改/已纳入管控" ≠ 已办结 → 保留；
- 官网公示"已完成清理"但同一诉求的其他事项仍未落实 → 按"已回复未办结"保留，摘要写明哪部分未落实。

## 四之二、社媒发现（小红书 / 微博 / 抖音等）

领导明确要求把小红书、微博、抖音纳入来源，按以下口径执行（看板按平台用不同颜色标签区分）：

- **只作线索发现，不进主台账、不计入线索统计**；
- 记录字段：`platform`（平台）、`title`、`summary`（≤100 字）、`url`（原帖链接）、`keyword`（检索词）、`found_at`、`status:"未核验"`；
- **只用搜索摘要**，不抓取登录后的正文/评论，不绕过登录；
- 不把帖子内容写成事实，不据此推断承办单位、办理状态、是否办结；
- 昵称、头像、手机号、住址一律不记录；
- 单独写入 `数据/社媒发现.jsonl`，报告单列「社媒发现（未核验）」一节，并提示用户自行甄别；
- 若社媒线索能在官方渠道找到对应记录，转入正常入库流程，并注明"社媒发现，官方核实"。

## 五、逐条核验流程

对每个候选线索：

1. **打开原文**：`web_fetch` 原文 URL。能取到正文 → 核验等级 A；仅取到标题/摘要 → 等级 B，并在条目中注明"正文前端渲染，凭搜索收录摘要记录，需人工复核"。
2. **提取事实**：发布时间、留言/工单编号、诉求人展示名（原样）、诉求内容、承办单位、回复内容与日期、当前状态。
3. **只写原文有的**：承办单位、处理结果、金额、时间节点，原文没有就写"原文未载"，**禁止推断补全**。
4. **状态依据**：引用判定所依据的原句（≤50 字），必须来自原文；禁止"单一来源待复核""未检索到回复"这类套话。确实无回复可引时，写"页面未见回复（抓取时间 YYYY-MM-DD HH:MM）"并说明页面无回复状态。
5. **交叉核验（可选）**：同一事件若有第二来源（另一平台/媒体），写入备注；无第二来源不扣分，但置信度不得标"高"。

### 两个日期必须分开
- `page_date`：页面发布/更新日期，优先从 URL 路径取（如 `/202611/t20261125_...` → 2026-11-25），或取页面标注的"发布时间"；
- `post_time`：留言/投诉实际发生日期，取正文里的"留言时间/反映时间"；
- 两者经常不同（URL 是发布日、正文是留言日），**不得混用**；台账 `published_at` 统一取 `page_date`，`post_time` 单列，避免把"7 天内"误判。

### 置信度
- **高**：正文直接可读，要素齐全，状态表述明确；
- **中**：仅摘要可读，或状态需从缺失的回复推断（如"页面无回复"）；
- **低**：仅有转述/截图/二手信息 → **不入库**，列入报告"待核"清单。

## 六、去重与状态更新

- 指纹：`渠道:编号`（如 `cjn:4114650`）；无编号时用"主体+问题+地点"关键词组合。
- 运行前读取台账全部指纹；命中已存在线索：
  - 状态未变 → 不重复列入"新增"，只在"状态更新"中记录最后核验时间；
  - 状态变化 → 在台账追加 `status_history`，报告"状态更新"区列出变化前后。
- 事件级去重（三同）：投诉人（或主体）相同/相近 + 地点相同 + 诉求内容相同 → 即使标题、来源、URL 不同，也合并为一条；`source_url` 放信息最全的主源，其余写入 `mirrors`；标题/摘要取最完整的一条；多源交叉成立时置信度可标"高"。
- 同一诉求人短期内多次投诉同一问题（重复投诉）→ 合并，状态标"重复投诉/办结不满意"。

## 七、脱敏规范（强制）

| 信息 | 处理 |
|---|---|
| 姓名 | 只保留姓氏+称谓（张先生/李女士）；原文全名一律不落库 |
| 手机号 | 保留前 3 后 4，中间打码（138****5678）；原文已打码则照录 |
| 身份证/银行卡/车牌 | 一律不录 |
| 住址 | 只到小区/街道；投诉人具体门牌、楼栋不录（诉求对象为房屋质量等必须定位时，只写到楼栋号，不写房号） |
| 聊天记录/录音 | 不转录，只写"原文附聊天记录/附件" |
| 未成年人 | 不披露任何可识别信息 |

原则：**投诉对象（企业、单位、小区）可实名**，因为涉及公共监督；**投诉人必须不可识别**。

## 九、台账写入

每入库一条，向 `数据\线索台账.jsonl` 追加一行 UTF-8 JSON（禁止中途改写已有行）：

```json
{"id":"WH-20261125-001","first_seen":"2026-11-25T14:45:00+08:00","last_verified":"2026-11-25T14:45:00+08:00","category":"民生","title":"","summary":"","complainant":"","channel":"","channel_url":"","ref_no":"","published_at":"","page_date":"","post_time":"","handler":"","status":"处理中","status_evidence":"","source_url":"","source_title":"","verify_level":"B","confidence":"中","fingerprint":"cjn:4113735","mirrors":[],"notes":"","status_history":[]}
```

- `published_at` = `page_date`（页面发布日），`post_time` 为留言发生日；旧条目可只留 `published_at`。
- `status_history` 只在状态变化时追加 `{"at":"","from":"","to":"","evidence":""}`。
- 剔除事项追加到 `数据\剔除记录.jsonl`，字段：`at, item, reason, media, url, closed_evidence`。

## 十、异常与降级

| 情况 | 处理 |
|---|---|
| 检索无结果 | 换同义检索式再试；仍无 → 如实写"本期该渠道未发现符合条件线索" |
| 原文打不开 | 保留链接与摘要，等级 B，置信度中，注明"访问失败，待人工复核" |
| 页面需登录 | 不绕过；记录"需登录，未采集" |
| 信息只有截图/转述 | 不入库，进"待核" |
| 本期 0 条 | 正常输出 0 条报告，列出覆盖清单与检索式，**不得凑数** |
| 某渠道零产出 | 换入口/换检索式再试；仍无则在"来源覆盖"写明，连续 3 期需找原因 |
| 运行超时 | 优先保证已核验条目写盘，再补来源说明 |

## 十一、发布前自检（逐条过）

1. 有原文 URL 吗？能打开吗？打不开是否标了 B？
2. 编号、发布时间、渠道是原文的吗？
3. 承办单位/结果是不是原文写的？有没有我"顺理成章"补的？
4. 状态判定有没有原文依据句？
5. 投诉人是否已脱敏？有没有出现房号、完整手机号？
6. 是否已被官媒报道且明确办结？→ 剔除并留痕。
7. 是否与台账重复？重复的是否走了状态更新？
8. 标题/摘要有没有情绪化、定性化、超出原文的词？

## 十二、禁止事项

- 禁止编造条目、编号、链接、承办单位、处理结果；
- 禁止把"已回复"写成"已解决"；
- 禁止采集非公开个人信息、禁止拼凑人物画像；
- 禁止复制大段原文（摘要 ≤150 字，引用 ≤50 字）；
- 禁止用"据传/网传/疑似"作为入库依据。
